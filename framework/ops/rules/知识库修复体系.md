# 知识库修复体系

> **定位**：`/check` 发现问题 → 本体系指导修复 → `/check --quick` 验证修复 → 闭环。
>
> **核心原则**：安全第一（备份+可回滚）、最小改动（只改有问题的）、**传播修复（改一必查三）**、可验证（修完能证明）。

---

## 一、修复五阶段

```
诊断 ──→ 规划 ──→ 执行 ──→ 验证 ──→ 归档
  │        │        │        │        │
  │        │        │        │        └─ 修复报告归档 + 版本记录更新
  │        │        │        └─ /check --quick → 确认问题已解决 + 无新增
  │        │        └─ 按批次逐项修复，每项先查传播表再修，修完即时验证
  │        └─ 生成修复计划：优先级/批次/波及范围/回滚方案
  └─ /check 定位问题 → 分类分级 → 输出基线报告
```

## 二、修复传播映射表

> **改了一个文件，必须检查相关联的文件。** 这是本体系区别于一般修复方案的核心机制。

### 2.2 传播表使用方式

LLM 执行修复时的标准操作流：

```
1. 确定变更类型 → 查传播表找到匹配行
2. 列出「必须同步的文件」清单
3. 逐文件检查是否需要修改
4. 需要改的 → 一并修改
5. 不需要改的 → 标注「已检查，无需修改」
6. 全部完成后 → /check --quick 验证
```

**示例**：修改了 `framework/ops/rules/文档转Markdown工具选型.md` 中的 LLM 执行协议（P04）

```
波及分析：
  ✅ Ingest完整流程.md —— 前置条件声明引用了本文档，已检查，无需改
  ✅ 知识库检查体系.md —— S8/C2/E6 关联本文档，已检查，无需改
  ✅ index.md —— 规则文件列表中有链接，已检查，无需改
  → 本次无额外文件需同步
```

## 三、修复三种类型

| 类型 | 说明 | 执行方式 | 风险 | 示例 |
|------|------|----------|:---:|------|
| **机械修复** | 路径替换、数字同步、YAML 补全 | 自动化脚本 | 低 | 全局替换旧路径、批量补 `updated` 字段 |
| **结构修复** | 创建缺失文件/目录、重建索引 | 脚本 + LLM | 中 | 创建缺失的规则文件骨架、重写 activation.md |
| **语义修复** | 规则矛盾、概念冲突、流程歧义 | LLM 判断 + 人类确认 | 高 | 消解两条矛盾的 G 层约束、重写模糊条款 |

## 四、安全边界

### 4.1 不可自动修复（必须人类确认）

- G 层约束增/删/改（走 G 层修改强制流程）
- T 层标签增/删
- 规则文件正文修改（非格式性）
- 文件删除 / 移动 / 重命名
- 版本号变更
- 语义修复全部内容

### 4.2 可自动修复（脚本执行 + log 记录）

- 路径替换（旧路径 → 新路径的纯文本替换）
- 数字同步（声明数字与实际一致）
- YAML 字段补全（`updated`、`review_date` 缺失）
- 创建缺失的占位文件（空骨架）
- 清理残留 `.tmp` 文件
- 文件命名规范化（去除通用名冲突）

### 4.3 自动修复脚本通用参数

```bash
--dry-run       # 预览模式，只显示会改什么，不实际修改（默认）
--execute       # 真实执行
--backup        # 执行前备份原文件到 .fix-backup/
--log           # 记录到 personal/data/log.md（默认开启）
--verbose       # 显示详细输出
```

## 五、修复执行流程

### 5.1 阶段 0：修复前准备

```
步骤 0：修复前准备（必须完成，缺一不可）

  ├─ 0.1 备份当前状态
  │     git add -A && git commit -m "checkpoint: 修复前快照 $(date +%Y-%m-%d)"
  │     git tag pre-fix-$(date +%Y-%m-%d)
  │
  ├─ 0.2 运行检查，生成基线报告
  │     /check --deep
  │     → 保存报告至 personal/system/queries/checkpoints/baseline-YYYY-MM-DD.md
  │
  ├─ 0.3 人类确认修复范围
  │     审阅问题清单（P0/P1/P2/P3）
  │     勾选本次修复项
  │     标注不修的项 + 原因
  │
  └─ 0.4 生成修复计划
        按优先级分批（P0 → P1 → P2 → P3）
        每项标注传播波及范围（查传播表）
        准备回滚方案
```

### 5.2 阶段 1-2：分批执行

```
批次 N：执行修复（按 P0 → P1 → P2 → P3 顺序，不可跳级）

  对批次内每项修复：

  ├─ 步骤 A：查传播表
  │     确定变更类型 → 匹配传播规则 → 输出波及文件清单
  │
  ├─ 步骤 B：执行修复
  │     ① 修改主体文件
  │     ② 逐项同步波及文件（需要改的改，不需要的标注「已检查」）
  │     ③ 记录到 personal/data/log.md
  │
  ├─ 步骤 C：即时验证
  │     对该修复项涉及的检查项单独重跑
  │     确认通过 → 标记 ✅
  │     未通过 → 回退该修复 → 分析原因 → 重试
  │
  └─ 步骤 D：批次提交
        git commit -m "fix(P0): {批次摘要}"
        → 进入下一批次
```

### 5.3 阶段 3：修复后验证

```
步骤 3：修复后验证（全部批次完成后）

  ├─ 3.1 全量复检
  │     /check --deep
  │     → 生成修复后报告
  │
  ├─ 3.2 基线对比
  │     对比基线报告 vs 修复后报告
  │     → 确认问题数下降
  │     → 确认无新增问题（P0/P1 新增 >0 → 阻断，必须处理）
  │
  ├─ 3.3 功能验证
  │     模拟 /ingest 流程（至少走通一遍）
  │     模拟会话启动 G 层加载
  │     → 核心功能正常
  │
  ├─ 3.4 版本号更新
  │     按版本管理规范更新版本号
  │     git tag v{新版本号}
  │
  └─ 3.5 修复报告归档
        写入 personal/system/queries/checkpoints/fix-report-YYYY-MM-DD.md
        更新版本记录表
```

## 六、回滚方案

### 6.1 触发条件

- 修复后 `/check --quick` 发现 P0 项未通过
- 修复引入 ≥3 个新问题
- 人类判断修复方向错误

### 6.2 回滚操作

```bash
# 方式 1：回滚整个修复批次
git reset --hard pre-fix-YYYY-MM-DD

# 方式 2：只回滚特定文件
git checkout pre-fix-YYYY-MM-DD -- <文件路径>

# 方式 3：恢复脚本备份
cp .fix-backup/<文件>.bak <原路径>
```

### 6.3 回滚后

1. 分析失败原因，记录到 personal/data/log.md
2. 调整修复方案
3. 重新执行修复（从阶段 0 开始）
4. 同问题连续 2 次回滚 → 升级为人类主导修复，LLM 不再自行尝试

## 七、修复工具包

### 7.1 工具清单

| 工具 | 用途 | 类型 | 状态 |
|------|------|:---:|:---:|
| `fix-stale-paths.py` | 全库旧路径 → 新路径替换 | 机械 | ✅ 已建 |
| `fix-inbox-clean.sh` | 清理 personal/data/inbox/ 过期文件和残留 .tmp | 机械 | ✅ 已建 |
| `fix-frontmatter.py` | YAML 字段补全 + 格式修复（复用 check-frontmatter.py --fix） | 机械 | ✅ 已建 |
| `fix-broken-links.py` | 批量修复 wikilink（自动匹配+置信度分级，人类确认） | 结构 | ✅ 已建 |
| `fix-numbers.sh` | 数字声明同步（G层/T层/R层/Lint 声明 vs 实际） | 机械 | ✅ 已建 |
| `kb-do.sh` | 原子操作（创建/重命名/删除） | 结构 | ✅ 已有 |

### 7.2 工具设计原则

1. **幂等**——重复执行不产生副作用
2. **可回滚**——备份原文件到 `.fix-backup/`
3. **有日志**——所有修改记录到 `personal/data/log.md`
4. **先预览**——默认 `--dry-run`，确认后 `--execute`
5. **查传播**——执行前输出波及文件清单

## 八、执行步骤

> 每种修复场景的具体操作步骤，LLM 和人类按此执行。

### 8.1 传播规则执行步骤

#### P01 · G 层约束增/删/改

```
LLM 执行步骤：
  1. 确认修改内容 → 走 G 层修改强制流程（警告模板+确认+git tag+log+交叉校验）
  2. 查波及文件：
     a. personal/data/log.md → 追加变更记录（日期 + 变更内容 + 受影响标签）
     b. T 层标签表 → 检查是否需要新增/修改标签
     c. 搜索全库引用 grep -rl "G[0-9]" personal/knowledge/ framework/ops/ → 逐文件检查是否需要更新
     d. 设计方案文档 → 同步更新（如适用）
  3. 逐波及文件确认：需要改的改，不需要的标注「已检查，无需修改」
  4. 验证：/check --quick
```

#### P03 · R 层规则文件增/删

```
LLM 执行步骤（新建规则）：
  1. 写入规则文件 → framework/ops/rules/<规则名>.md（含完整 YAML frontmatter）
  2. 查波及：
     a. index.md → 在对应子目录区域追加 - [[framework/ops/rules/<规则名>]] —— summary
     b. AGENT.md T 层表 → 如需新标签，走 G 层修改流程
     c. 系统操作菜单.md → 如是新操作指令，追加到对应表格
     d. activation.md → 在对应目录区域追加文件名
  3. personal/data/log.md → 追加创建记录
  4. 验证：/check --quick

LLM 执行步骤（删除/归档规则）：
  1. 搜索全库引用：grep -rl "[[framework/ops/rules/<规则名>]]" personal/knowledge/ framework/ops/ → 列出所有引用者
  2. 逐引用者移除或更新链接
  3. index.md → 移除对应条目
  4. AGENT.md T 层表 → 移除关联标签（如该标签无其他规则）
  5. 移动文件到 personal/knowledge/archive/（非直接删除）
  6. personal/data/log.md → 追加归档记录
  7. 验证：/check --quick
```

#### P05 · 规则文件改名/移动

```
LLM 执行步骤：
  1. 确定新旧路径
  2. 全库搜索旧名引用：
     grep -rn "旧文件名" personal/knowledge/ framework/ops/ --include="*.md"
  3. 对每个引用文件：替换 [[旧名]] → [[新名]]（或 [[旧名|别名]] 仅改目标）
  4. 更新 index.md 中对应条目
  5. 更新 AGENT.md T 层表（如涉及标签路径）
  6. 更新 系统操作菜单.md（如涉及操作入口）
  7. 执行重命名：mv 旧路径 新路径（或用 kb-do.sh rename）
  8. personal/data/log.md → 追加改名记录
  9. 验证：python framework/engine/scripts/check-links.py --repo . --mode broken → 确认无新增断链
```

#### P06 · 增/删/改脚本

```
LLM 执行步骤（新建脚本）：
  1. 写入脚本文件 → 遵循架构约定（--repo/--json/路径自定位）
  2. 语法检查：python -m py_compile <脚本路径>
  3. 查波及：
     a. 引用该脚本的规则文件 → 确认命令示例是否需要更新
     b. 系统操作菜单.md → 如是用户入口，追加
     c. requirements.txt → 检查 import 是否已有对应包
  4. personal/data/log.md → 追加创建记录
  5. 验证：python framework/engine/scripts/check-script-refs.py（待建）或手动 grep

LLM 执行步骤（修改脚本接口）：
  1. 确认变更内容（参数/输出格式/路径）
  2. 搜索脚本引用：grep -rl "<脚本名>" framework/ops/ personal/knowledge/ --include="*.md"
  3. 逐引用文件更新命令示例和参数说明
  4. 验证：/check --quick
```

#### P08 · 改目录结构

```
LLM 执行步骤：
  1. 确定变更（新建/删除/重命名哪个子目录）
  2. 搜索旧路径引用：
     grep -rn "personal/knowledge/<旧子目录>" framework/ops/ personal/knowledge/ --include="*.md"
  3. 更新波及文件（按优先级）：
     a. index.md → 更新导航链接
     b. activation.md → 更新目录清单
     c. 所有含旧路径引用的 .md → 逐文件替换
     d. 脚本中的路径常量 → 更新（如 TARGET_TO_SOURCE）
  4. 执行目录操作（mkdir/mv/rmdir）
  5. personal/data/log.md → 追加变更记录
  6. 验证：/check --quick
```

### 8.2 修复类型执行步骤

#### 机械修复 · 路径替换

```bash
# 场景：全库替换旧路径 → 新路径
# 步骤 1：预览影响范围（不改文件）
grep -rn "旧路径模式" personal/knowledge/ framework/ops/ --include="*.md"

# 步骤 2：确认替换无误（检查上下文）
# LLM 抽查 5-10 处匹配，确认确实是旧路径引用而非正文内容

# 步骤 3：人类确认后执行替换
# 方式 A：sed 批量替换（简单场景）
find personal/knowledge/ framework/ops/ -name "*.md" -exec sed -i 's|旧路径|新路径|g' {} +

# 方式 B：Python 脚本（复杂场景，需判断上下文）
python framework/engine/scripts/fix-stale-paths.py --old "旧路径" --new "新路径" --dry-run
python framework/engine/scripts/fix-stale-paths.py --old "旧路径" --new "新路径" --execute --backup

# 步骤 4：验证
python framework/engine/scripts/check-links.py --repo . --mode broken
python framework/engine/scripts/check-hardcoded-paths.py --repo .
```

#### 机械修复 · YAML 字段补全

```bash
# 场景：批量补填缺失的 updated 字段
python framework/engine/scripts/check_stale.py --repo . --mode field --fix

# 场景：批量补填缺失的 frontmatter 字段（需谨慎）
python framework/engine/scripts/check-frontmatter.py --repo . --fix
# ⚠️ --fix 仅自动补填 updated 字段，tags/status 需人类判断后手动补
```

#### 机械修复 · 清理 personal/data/inbox/

```bash
# 步骤 1：预览
python framework/engine/scripts/check-inbox.py --repo . --max-age 7

# 步骤 2：手动清理过期文件
# 过期 .md → 确认是否需要 → 删除或移动到 personal/raw/
# 残留 .tmp → 直接删除
find personal/data/inbox/ -name "*.tmp" -delete

# 步骤 3：重新检查
python framework/engine/scripts/check-inbox.py --repo .
```

#### 结构修复 · 创建缺失文件

```
LLM 执行步骤（以缺失规则文件为例）：
  1. 确认文件用途（从引用上下文推断）
  2. 生成文件内容：
     - YAML frontmatter（tags/status/summary/created/updated）
     - 标准章节（约束/正例/反例/例外/关联）
     - 标注 [待完善] 标记
  3. 人类审阅 → 确认后写入
  4. 查传播表 P03 → 更新 index.md + 关联文件
  5. 验证：/check --quick
```

#### 结构修复 · 重写 index.md 或 activation.md

```
LLM 执行步骤（以 activation.md 为例）：
  1. 扫描实际目录结构：find personal/knowledge/ framework/ops/ -type d
  2. 对比旧 activation.md → 列出缺失/多余条目
  3. 生成新版内容（按目录树结构）
  4. 人类审阅 → 确认后写入
  5. 查传播表 P08 → 检查是否有路径变更需要同步
  6. 验证：python framework/engine/scripts/check-links.py --repo . --mode index
```

#### 语义修复 · 规则矛盾消解

```
LLM 执行步骤：
  1. 精确描述矛盾：规则 A 说 X，规则 B 说 Y，冲突场景是 Z
  2. 列出两种消解方向 + 各自影响范围
  3. 输出《反馈冲突提示》（走 G3 流程）
  4. 等待人类裁决（不可自行裁决）
  5. 裁决后：
     a. 修改被裁定为正确的规则
     b. 在另一个规则中标注「已被规则 X 覆盖」
     c. 查传播表 P01/P04 → 同步波及文件
     d. personal/data/log.md 追加裁决记录
  6. 验证：/check --quick
```

### 8.3 LLM 修复执行协议

> LLM 每次执行修复时的标准协议，强制遵守。

```
┌─ 修复执行协议 ─────────────────────────────┐
│                                              │
│  Step A: 查传播表                            │
│    确定变更类型 → 匹配传播规则 → 输出波及清单  │
│                                              │
│  Step B: 备份                                │
│    git add -A && git commit -m "checkpoint"  │
│    （或对单文件 cp 到 .fix-backup/）          │
│                                              │
│  Step C: 执行修复                            │
│    ① 修改主体文件                             │
│    ② 逐波及文件：需要改的改，不需要的标注      │
│    ③ 记录到 personal/data/log.md                           │
│                                              │
│  Step D: 即时验证                            │
│    跑受影响的检查脚本 → 确认通过               │
│    未通过 → 回退该修复 → 分析 → 重试          │
│                                              │
│  Step E: 人类确认（仅不可自动修复）            │
│    展示修改内容 + 波及分析 → 等确认            │
│                                              │
└──────────────────────────────────────────────┘
```

### 8.4 常见修复场景速查

| 场景 | 传播规则 | 修复类型 | 关键命令 |
|------|:---:|:---:|------|
| 文件改名 | P05 | 结构 | 全库 grep 旧名 → sed 替换 → check-links.py --mode broken 验证 |
| 新建规则 | P03 | 结构 | 写文件 → 更新 index.md + 菜单 + log |
| 改 G 层 | P01 | 语义 | 走 G 层修改流程（警告+确认+tag+log+校验） |
| 补 YAML 字段 | — | 机械 | `check_stale.py --mode field --fix` / `check-frontmatter.py --fix` |
| 清 inbox | — | 机械 | `check-inbox.py` 定位 → 手动清理 → 复检 |
| 消解矛盾 | P01+P04 | 语义 | 描述矛盾 → 列方案 → 等裁决 → 改规则+波及文件 |
| 版本升级 | P10 | 机械 | 改 AGENT.md → 更新 personal/data/log.md → 更新设计方案 → /check --quick |
| 修断链 | P05 | 结构 | 逐断链查目标是否存在 → 更新链接或移除 |
| 删规则 | P03 | 结构 | 全库搜引用 → 移除/更新引用 → 搬 archive → 更新索引 |

## 十、风险矩阵

| 风险 | 概率 | 影响 | 应对 |
|------|:---:|:---:|------|
| 路径替换误伤正文 | 中 | 中 | `--dry-run` 预览 + 只替换 wikilink 和代码块中的路径 |
| 数字同步改错声明 | 低 | 高 | 只改声明处，不改实际定义；改前确认实际值 |
| 传播遗漏（改了主体忘了波及文件） | **高** | **高** | **强制查传播表** + `/check --quick` 复检会自动发现断链 |
| 修复引入新断链 | 中 | 中 | S3 断链检查作为必选验证项 |
| 语义修复人类不认可 | 中 | 低 | 保留原状 + 标注「待讨论」+ 不阻塞机械修复 |
| 批次间依赖未处理 | 低 | 高 | 严格 P0→P1→P2→P3 顺序，不跨级 |

## 十一、与检查体系的闭环

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ /check   │ ──→ │ 修复体系  │ ──→ │ /check   │
│ 发现问题  │     │ 查传播表  │     │ --quick  │
│ 输出基线  │     │ 分批修复  │     │ 验证闭环  │
└──────────┘     └──────────┘     └──────────┘
      ↑                                  │
      └──────────── 循环改进 ────────────┘
```

| 场景 | 检查 | 修复 |
|------|------|------|
| 日常运维 | `/check`（周检查） | 按需修复 P0/P1 |
| 版本升级 | `/check --deep`（月检查） | 修复发现的问题 → `/check --quick` |
| G 层修改 | `/check --quick`（变更后） | 查传播表 P01 → 同步波及文件 |
| 模板发布 | `/check --full`（全量） | 全量修复 + 人工抽查 |
| 接手知识库 | `/check --full` | 首次全量修复历史遗留 |
