# 反馈闭环流程

> 对齐 V2.15 原始设计·规则六

## 约束

| 反馈类型 | 处理方式 |
|------|------|
| 口述反馈 | LLM 回显确认 → 写入 `raw/feedback/` |
| 书面反馈 | 直接引用原文 → 写入 `raw/feedback/` |
| 中途好评/差评 | 会话结束时回溯确认，不打断当前任务 |
| 无回应 | 仅追加 `raw/sessions/` 摘要，不提炼任何正/反模式 |
| 任务完成反馈(G19) | 实质性任务完成后追加「[G19] 满意/有改进空间？」反馈行，与 G12/G15/G17/kb-query 互斥，连续 3 次跳过→暂停由 G13 兜底 |

**硬约束**：未收到人类明确确认的反馈，不得进入 `raw/feedback/`。

评价模糊时先追问再写入，不猜测：

| 模糊类型 | 用户说法示例 | 追问 |
|------|------|------|
| 目标不明 | 「这次回复不太好」 | 「是内容不对、格式不对、还是太啰嗦了？」 |
| 范围不明 | 「模板那个规则有问题」 | 「是规则本身不合理，还是执行时总触发误报？」 |
| 程度不明 | 「有点太长了」 | 「期望的长度大概是现在的 50% 还是 30%？」 |
| 对比缺失 | 「上次那个更好」 | 「上次的哪个方面更好？结构、措辞还是内容？」 |

## 正例

> 用户中途说「这个表格格式不错」→ LLM 标记暂存，不打断当前任务 → 会话结束时回溯确认 → 写入 `raw/feedback/positive/` → 下次 Ingest 提炼为 `ops/patterns/`

## 反例

> 用户说「不好」→ LLM 不追问直接猜测原因并修改规则 → 改错了方向
> 会话结束时不确认就直接写入 feedback/ → 违反硬约束

## 会话结束时

1. **主动询问入库**：会话自然结束→主动询问「是否入库？」。用户确认后一步写入：直接生成会话摘要并写入 `raw/sessions/`，写入后回复「📝 已写入：[文件名]」。
2. **即时校验 YAML**：写入 `raw/sessions/` 时即时校验 YAML frontmatter（必含 `status` 和 `summary` 字段），缺字段→自动补齐后写入。

## 例外

### 例外1：用户提前终止
- 触发条件：用户说「今天就这样」「不记了」
- 例外行为：仅追加 sessions/ 摘要，不收集反馈
- 标志动作：标注 `[跳过反馈收集]`

## 文件修改确认（原 文件修改确认.md + _可自动执行操作清单）

### 约束

1. 涉及文件修改、删除、重命名等破坏性操作时，必须先向用户确认后再执行
2. 确认格式：我计划 [做什么]，文件：[路径]，影响：[说明]。可以吗？
3. 用户明确说「直接改」「不用问」「继续」时跳过确认
4. Read、Glob、Grep 等只读操作不受此限

### 例外：用户明确放行
- 触发条件：用户说「直接改」「不用问」「继续」
- 例外行为：该轮操作可跳过确认，仅对该轮有效

### 可自动执行 vs 必须确认

**非破坏性操作（high conf → 自动执行）**：queue/log 标记、YAML 补全/修复、新建规则文件/会话摘要/index 条目、输出报告

**破坏性操作（必须 G12 确认）**：修改正文/YAML已有值、删除、移动/重命名、G层变更、页面合并

## kb-query 反馈→文章回写

当用户通过 kb-query 反馈指出回答"不准"且根因为 tags 不准时：

1. 定位涉事文章（从检索命中列表找）
2. 修正 tags → 回写文章 frontmatter（非破坏性操作，高置信度下自动执行）
3. 记录修正日志：`raw/sessions/kb-query-log.jsonl` 追加 `fix_applied: true, fix_type: "tags_correction"`
4. 同域扫描：`grep -rl "tags:.*<旧tag>" knowledge/learning/<domain>/` → 批量检查同类问题
5. 同域 ≥2 篇文章需同样修正 → 触发 G15 主动沉积（提议新建反模式）

此为非破坏性操作（仅修改 frontmatter tags 行），高置信度下自动执行+log 记录。如涉及 taxonomy 缺 subdomain → 追加到 tag-taxonomy.yaml，此操作需 G12 确认。
