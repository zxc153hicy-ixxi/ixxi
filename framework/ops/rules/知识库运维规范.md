# 知识库运维规范

## 约束

1. 所有规则、反馈、行为准则统一存储在 `ops/rules/` 下
2. 新建规则：写入 `ops/rules/<规则名>.md` → 更新 `index.md`
3. 检查目录必须用 `find <dir> -type f` 递归搜索，禁止仅 `ls` 根目录（G9）
4. 涉及 Obsidian 等软件 UI 操作时，必须先确认用户版本号（G10）
5. Ingest ≥1 次/周，>7 天提醒，>30 天告警
6. 每次会话启动时读取 `knowledge/projects/知识库管理/用户画像.md`，画像为空则跳过（G8）
7. **废弃联动**：将文件 status 改为 deprecated 或 superseded 时，若文件仍在 `ops/rules/`、`ops/anti-patterns/` 或 `knowledge/` 其他活跃子目录，必须主动提示用户「是否移到 `knowledge/archive/`？」

## 正例

> 用户提出新规则 → LLM 写入 `ops/rules/xxx.md`（含完整 YAML frontmatter）→ 更新 `index.md` → log 记录 → 完成
> 排查目录内容 → `find knowledge/ ops/ -type f -name "*.md"` → 完整列表

## 反例

> 用户提了一条规则，LLM 写入 `~/.claude/projects/C--/memory/` → 没有写入知识库 → 下次会话找不到
> 用 `ls knowledge/ ops/` 扫一眼就说「都有」 → 实际遗漏了子目录文件

## 设计与实现同步

对知识库做结构性修改时，必须同步更新设计方案文档（`Desktop/本地知识库搭建方案/`）：

**需要同步的**：
- G 层约束新增/修改/删除
- T 层标签新增/修改/删除
- R 层规则文件新增/归档
- 新机制引入（如半自动化、置信度分级）
- 目录结构变更
- 版本号升级

**不需要同步的**：
- knowledge/archive/小说创作/ 创作内容
- knowledge/archive/知识库管理/iterations/ 迭代记录
- raw/ 中的会话和反馈
- patterns/anti-patterns 的新增条目
- 纯数据内容的新增和修改

同步方式：修改对应设计方案模块 → 一致性检查 → 更新版本记录表。

## 模板同步

修改系统文件后，主动提醒用户「模板需要同步，是否导出？」。

导出方式：执行 `engine/templates/export-template.sh`，生成 `<知识库根>-Template`。
导出脚本本身不进入模板。

## 存量回溯

新机制/规则/流程上线时，必须对存量数据执行一次全量回溯：

1. 定义跟踪范围（哪些数据需要纳入新机制）
2. 增量数据自动跟踪
3. **跑 `/audit` 扫描存量**——发现遗漏→自动标记或入队
4. 确认全部覆盖后，机制生效

禁止只做增量不管存量。

## 技术强制识别

发现文本约束型的规则可能被绕过时，主动告知用户可以技术强制的方案（pre-commit hook、校验脚本、阻断机制等）。用户决定是否实施。

## 脚本同步

规则变更时，必须检查受影响的自动化脚本并同步更新：

| 规则变更类型 | 需检查的脚本 |
|------|------|
| YAML 字段新增/修改 | lint-data.sh · check-template.sh |
| G 层约束新增/删除 | check-cross-validate.sh · pre-commit hook |
| 目录结构变更 | stats.sh · check-template.sh |
| 设计方案版本号变更 | check-design-sync.sh |
| 版本号格式变更 | check-design-sync.sh · check-cross-validate.sh |
| 新增/删除检查项 | lint-data.sh · check-template.sh |
| 安全模式变更 | scan-sensitive.sh |

变更后立即跑受影响的脚本验证。脚本过期未同步 → 告警。

## 内容版本管理

个人知识会更新迭代，旧版本需显式标记以防混淆。

### YAML 字段约定

| 字段 | 类型 | 用途 | 写入时机 |
|------|------|------|------|
| `type` | `literature` \| `permanent` | 区分摘录与自己的理解 | Ingest Step 3 必设 |
| `updated` | date `YYYY-MM-DD` | 最后修改日期 | Ingest 自动填入；手动编辑时自行更新 |
| `review_date` | date `YYYY-MM-DD` | 计划复核日期（可选） | 创建时预估（建议 +90 天） |
| `superseded_by` | wiki 链接 | 指向取代本页的新页面 | 知识更新时手动设置 |
| `replaces` | wiki 链接 | 指向被本页取代的旧页面 | 新页面创建时手动设置 |

### 知识版本生命周期

```
active → superseded → archived
  │        (Lint提醒搬家)
  └────────────────────────→ archived
         (直接归档，无需 superseded 过渡)
```

- **active**：当前有效知识
- **superseded**：已被新版本取代，保留 `superseded_by: "[[新页面]]"` 指向新版。Lint #17/#18 扫描时提醒搬家
- **archived**：已移至 `knowledge/archive/`，保留历史记录

### 更新旧知识的操作流程

1. 创建/修改新页面，YAML 加 `replaces: "[[旧页面标题]]"`
2. 修改旧页面：`status: superseded` + `superseded_by: "[[新页面标题]]"`
3. 下次 `/lint` 提醒将 superseded 页面移至 archive

## 文件命名规范

**默认使用中文命名。** 仅以下场景保留英文：

| 场景 | 示例 | 原因 |
|---|---|---|
| 代码/脚本文件 | `.sh` `.js` `.py` | 中文名可能导致执行报错 |
| 系统入口文件 | `AGENT.md` `activation.md` `queue.md` `log.md` `session-notes.md` | 被 hook/脚本硬编码引用 |
| 版本号 | `v0.5.0.md` `V2.15-方案摘要.md` | 版本号本身是数字 |
| 日期前缀 | `2026-06-27-会话摘要.md` | ISO 日期标准格式 |
| 技术专有名词 | `ixxi-agent-设计文档.md` | 项目名/协议名保留原文 |

**命名原则：**
- 文件名 = 一句话概括内容，看完名字就知道是什么
- 禁止通用名：`index.md` `设定.md` `大纲.md` `提示词.md`（不含上下文无法识别）
- 同目录下统一前缀：如 `项目_` 前缀统一创作内容
- 同名文件禁止：全库范围内文件名必须唯一
