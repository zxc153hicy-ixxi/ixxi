# 多 Agent 工作流低效浪费

## 触发场景

用多 agent 并行工作流处理需要"读取→分析→写入"的任务时，agent 只返回分析结果不执行写入，导致大量 token 消耗无产出。

## 典型案例

一次内容富化工作流：31 个 agent 并行分析 30 篇文档，每个 agent 正确读取内容并返回结构化 JSON（标签/摘要），但**没有任何文件被实际修改**。消耗 70 万 token，产出为 0。

失败原因：agent 被设计为"分析并返回结果"，但没有在 pipeline 中执行写入步骤。

## 根因

- 并行工作流适合纯分析/审查任务，不适合需要修改文件的读写混合任务
- agent 返回结构化数据没问题，但写回文件的步骤缺失
- 批量小文件修改的最优方式不是并行 fan-out，而是串行处理（省去 agent 启动开销）

## 预防

1. 批量文件修改（读→分析→写回）：**串行处理**，不用并行工作流
2. 并行工作流专用于：纯分析、审查、验证、对账——不需要写回文件的任务
3. 如果非要用工作流写文件，pipeline 必须包含独立的写入 stage
