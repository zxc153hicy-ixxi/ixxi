# 命名规范先讨论后落笔

制定命名规范等约定性规则时，先拿出草案让用户审视，逐条确认设计选择，用户不满意时重新 brainstorming 而非在旧稿上修补。规则属于"共识"类产物，必须用户认同每一行的设计意图。

## 核心原则

1. 先搞清楚用户不满意什么，再改，不猜
2. 逐条确认核心设计选择（分隔符、版本位置、日期处理）
3. 每条规则有正例和反例，正例来自实际项目文件
4. 规则应尽量少——能合并的合并，能用一句话的不写三段

## 本次案例

V1 写了 18 条（中文下划线、英文连字符、日期前缀、目录差异化……）→用户说"不满意"→brainstorming 发现核心诉求是"望文知义"和"尽量简洁"→V2 精简到 16 条，中文直连、日期不进文件名。

## 反例

> 用户说"设计一下命名规范"→LLM 直接写一个 50 条的规范文件→用户看两行就不看了
