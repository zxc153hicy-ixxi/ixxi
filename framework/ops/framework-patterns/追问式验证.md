# 追问式验证

验证一个机制/修复时，不要停在「status 归零」「脚本跑通」就宣布完成，要反复追问到「真实触发」那一层。

## 核心追问（按穿透深度）

1. **实际应用了吗**——不只是「脚本跑通了」，是「真实场景里真的用了吗」
2. **真实触发了吗**——挂载型机制（hook/事件），不是 bash 直接跑，是真实 commit/真实事件走到了它
3. **真的防住了吗**——红队测试，故意违规，看机制拦不拦

## 实例

本次会话，用户反复追问「验证过吗」「实际应用」「能不能防住」，逼出了三个藏在「表面通过」下的真问题：

- **挂载错位**：hook 挂到 `.claude/kb`，但 git 实际调 `.git/hooks`——红队测试用 bash 直接跑，绕过了真实路径
- **中文编码假阴性**：验证命令传中文给 Python，GBK/UTF-8 不一致导致匹配不到，把「能防住」误判成「漏了」
- **流程强制不可靠**：G15 规则文字是「LLM 可忽略的建议」，靠自觉执行的流程步骤，无法真触发验证

## 为什么有效

「表面通过」是最容易自欺的地方——status 归零、脚本跑通、规则写全，都可能是「假阴性」（看似工作，实际空转）。追问逼到「真实触发」那一层，假阴性才显形。
