# 过度脚本化

> 反模式 = 踩过的坑：把本可直接语义分析解决的事硬写成脚本。

## 发生了什么

在运维/治理类工作中，多次手写脚本来做**比对/查询/匹配**类操作——这些操作直接读文件、语义理解即可完成。例如：

| 情况 | 做了（过度的） | 应该做 |
|------|------|------|
| 源目录文件 ↔ 目标目录入库比对 | 写脚本标准化文件名+匹配 | 读两边目录，语义判断是否匹配 |
| 转换目录 ↔ 目标目录同步检查 | 写脚本逐文件对比 | 看文件名列表即可判断 |
| 脚本重叠检测 | 设计 AST Jaccard 相似度算法 | 读代码语义判断重叠 |

## 根因

「工具优先」被机械理解为「能写脚本就写脚本」。缺失了一条判断：**在写脚本之前，先问「这个操作用直接分析能做吗？」**

## 决策模型

```
需要精确一致 + 重复执行 ≥3次  →  写脚本
需要语义理解 + 上下文判断       →  直接分析
两者都满足                      →  脚本 + 语义判断（混合）
```

## 正确做法

1. 写脚本前先判断是否可用语义分析替代
2. 只有在「需要精确一致」或「重复执行 ≥3 次」时才值得封装脚本
3. 语义分析能胜任的比对/查询/匹配，直接做，不要过度工程化
