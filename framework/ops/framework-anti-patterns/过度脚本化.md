# 过度脚本化

> 反模式 = 踩过的坑：把 LLM 本来就能做好的事硬写成脚本。

## 发生了什么

在知识库运维中，多次用 `execute_code` 手写 Python 脚本来做**比对/查询/匹配**类操作——这些操作 LLM 直接读文件、语义理解即可完成。例如：

| 情况 | 做了（过度的） | 应该做 |
|------|------|------|
| raw/inbox PDF ↔ knowledge/ .md 入库比对 | 写脚本标准化文件名+匹配 | LLM 读两边目录，语义判断是否匹配 |
| .inbox/converted ↔ knowledge/ 同步检查 | 写脚本逐文件对比 | LLM 看文件名列表即可判断 |
| 脚本重叠检测（E8） | 设计 AST Jaccard 相似度 | LLM 读代码语义判断重叠 |

## 根因

G18「工具优先」被机械理解为「能写脚本就写脚本」。缺失了一条判断：**在写脚本之前，先问「这个操作用 LLM 直接分析能做吗？」**

## 决策模型

```
需要精确一致 + 重复执行 ≥3次  →  写脚本
需要语义理解 + 上下文判断       →  LLM 直接分析
两者都满足                      →  脚本 + LLM 判断（A+L 混合）
```

## 怎么修的

1. 用户画像新增偏好「脚本不为默认选项」
2. G18 工具优先的操作流程增加第一步：先判断是否可用 LLM 语义分析替代
3. 检查体系 E8（脚本重叠检测）从 [A] 改为 [L]，不再设计自动化脚本
