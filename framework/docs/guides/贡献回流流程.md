# personal → framework 贡献回流流程

> **对应不变量 I7「显式贡献流程」**：任何内容从个人环境（`personal/`）晋升到开源通用层（`framework/`），都必须走显式、可追溯的贡献流程，而不是悄悄复制粘贴。
> 全程六步：**判据检查 → 脱敏 → 贡献包 → PR → 审查 → 合并**。每一层都通过才允许进入 `framework/`。

## 0. 流程总览

| 步骤 | 动作 | 产物 / 关卡 |
|---|---|---|
| 1 | 判据检查 | 通过「换个陌生使用者还有用吗」 |
| 2 | 脱敏 | `scan-sensitive.sh` 通过 + 人工剥离完成 |
| 3 | 贡献包 | `contribution.json` + 内容文件 |
| 4 | PR | fork → 分支 → `git commit -s` → push → PR |
| 5 | 审查 | 机械审查 + 语义审查（审查团 + 维护者） |
| 6 | 合并 | 维护者合并，进 `framework/` 并留档 |

---

## 第 1 步：判据检查「换个陌生使用者还有用吗」

先逐条勾选下面**三问**（三问全过才通过）：

- [ ] **能否干净环境独立跑通？** —— 换一台空机器、只装框架依赖，这段内容能否独立复现价值（不依赖你的本机路径 / 账号 / 配置）
- [ ] **能否脱离创始人场景复现？** —— 剥离你的个人项目、故事、偏好后，内容是否仍完整可用
- [ ] **是否有第二使用者信号？** —— 是否被 ≥2 个独立使用者请求/验证，或有客观通用价值（机制 / schema / 通用规则 / 通用教训）

> **三问全过** → 进 `framework/`；**任一不过** → 留 `personal/`。

判据不过 → **流程在此终止**，不回退、不强行晋升。无法判断时，在 PR 描述里写明判断过程，交审查团裁定。

## 第 2 步：脱敏（scan-sensitive + 人工剥离）

任何 personal 层内容进入开源前必须脱敏，**两步缺一不可**：

### 2.1 机械扫描（scan-sensitive）

运行框架自带敏感扫描，排除密钥 / 个人数据：

```bash
bash framework/engine/templates/scan-sensitive.sh
```

- 覆盖检测：身份证 / 银行卡 / 手机号 / 邮箱 / API 密钥（sk-）/ JWT / AWS Key / 密码明文。
- 命中任何一项 → **不通过**，先剥离再重跑，直到输出 `✅ 未发现敏感信息`。

### 2.2 人工剥离（上下文脱敏）

机械扫描管不到「语义级」的个人绑定，需要人工逐项剥离：

| 剥离对象 | 例子 | 处理 |
|---|---|---|
| 个人数据 | 真实姓名、账号、路径 | 替换为占位符（`<你的账号>`）或删除 |
| 环境绑定 | `/home/你的用户名/`、本机绝对路径 | 改为相对路径 / 通用路径 |
| 个人场景 | 特定项目的业务上下文、个人工作流 | 抽象为通用场景描述 |
| 个人故事 / 偏好 | 具体事件、个人故事 | 删除或泛化为通用教训 |
| 内部命名 | 个人项目名、私有服务名 | 替换为通用命名 |

剥离完成后自查：**文件里还能看到「这是某个具体的人 / 环境」的证据吗？** 能 → 继续剥离；不能 → 通过。可对照 security-agent 审查清单复核（见 [[framework/.claude/agents/security-agent]]）。

## 第 3 步：贡献包（contribution.json）

把脱敏后的内容组织成**贡献包**——一个 `contribution.json` 元数据 + 内容文件。贡献包让每笔晋升都可审计、可追溯。

### 3.1 contribution.json 结构

```json
{
  "schema_version": "1.0",
  "contribution_id": "C-doc-001",
  "title": "一句话标题",
  "type": "mechanism",
  "summary": "这段内容提供什么通用价值",
  "judgment": {
    "universal_value": "为什么对陌生使用者有用（判据论证）",
    "personal_dependencies_removed": ["已剥离的个人依赖清单"]
  },
  "compliance": {
    "desensitized": true,
    "scan_sensitive_passed": true,
    "original_work": true,
    "dco_signed": true,
    "versioned": true
  },
  "target_path": "framework/",
  "files": [
    {"path": "framework/.../目标文件.md", "note": "说明"}
  ],
  "author": "@github_handle",
  "created": "2026-08-14"
}
```

### 3.2 字段说明

| 字段 | 要求 |
|---|---|
| `type` | `capability` / `skill` / `rule` / `pattern` / `doc` / `mechanism` |
| `judgment` | 必填：判据论证 + 已剥离依赖，供审查团直接核对 |
| `compliance` | 必填：`desensitized`（人工剥离完成）、`scan_sensitive_passed`（扫描通过）、`original_work`（有权贡献，DCO 语义）、`dco_signed`（签名）、`versioned`（可迁移对象带 version，不变量 I10） |
| `target_path` / `files` | 指明晋升落点，与 PR 改动一一对应 |

### 3.3 与文件一起提交

贡献包 = `contribution.json` + 内容文件，放在同一分支同一 PR 中。`contribution.json` 缺失或字段不全 → 机械审查直接退回。

## 第 4 步：PR

按 [[CONTRIBUTING]] 的路径走：**fork → 创建分支 → 提交（`git commit -s` 带 DCO 签名）→ 推送 → 发起 PR**。

PR 描述必含三件套：
1. **改动目的**：要晋升什么、为什么。
2. **判据过程**：第 1 步「换个陌生使用者还有用吗」的判断说明。
3. **验证方式**：如何证明改动有效（改计数就重新数、建 skill 就确认在列表、改文档口径就实测核对）。

## 第 5 步：审查（机械 + 语义）

双关审查，任一不过即退回：

### 5.1 机械审查（自动化 + 硬关卡）

| 检查项 | 判据 |
|---|---|
| DCO | 所有提交带 `Signed-off-by` 签名 |
| CLA | 外部贡献者首次 PR 签署 CLA（cla-assistant 自动校验） |
| 敏感扫描 | `scan-sensitive.sh` 通过，无密钥 / 个人数据残留 |
| schema | `contribution.json` 结构合法、必填字段齐全 |
| version | 可迁移对象带 `version`（不变量 I10） |
| 断链 / 计数 | 文档交叉引用不悬空、引用计数核对一致 |
| 抽查样本 | 维护者随机抽查 contribution 声明的「已剥离依赖」，grep 个人词表 / 路径验证剥离真实（防声明与实际不符） |
| 原创性 | git diff 新增内容与已知来源比对，无复制粘贴嫌疑（抄袭检查） |

### 5.2 语义审查（审查团 + 维护者）

- **审查团**：质量 / 安全 / 架构等审查 agent（见 [[framework/.claude/agents]]）从各自视角审查。
- **维护者终审**：核对判据是否成立（「换个陌生使用者还有用吗」）、迁移性、可验证性、是否破坏现有不变量。
- 判据有争议 → 审查团裁定；对晋升 / 合并行使否决权 → 按 [[MAINTAINERS]] 第 3 / 4 节流程处理治理问题。

## 第 6 步：合并

- 机械 + 语义全部通过 → 维护者合并进 `framework/`。
- 合并后同步：更新相关索引 / 交叉引用（若涉及）、记录 contribution 留档（contribution_id 可查）。
- **版本号由维护者统一递增**：贡献者不在 PR 里自带版本号（如 `v0.1.1-我的定制`），合并后由维护者按 semver 规则统一递增并更新 CHANGELOG。
- 合并即完成从 `personal/` 到 `framework/` 的显式晋升，全程可追溯。

---

## 留在 personal 的常见情形（不回流）

- 个人场景注册、个人 skill、个人数据与知识、个人工作流、个人故事——这些对陌生使用者无通用价值。
- 含敏感信息且无法 / 不值得剥离的内容。
- 判据不确定、无法给出论证的内容。
