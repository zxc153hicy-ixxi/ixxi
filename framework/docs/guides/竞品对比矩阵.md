# 竞品对比矩阵

> 目的：讲清 ixxi 的差异化。一句话定位 + 对比矩阵 + 「ixxi 不是什么」 + 诚实的场景选择建议。
> 写作原则：客观中立，不吹捧、不贬低竞品——每个工具在其生态位都成立。

## 一、一句话定位

> **ixxi 是 Agent 的使用层，LangChain 是 Agent 的构建层。**

展开三句：

1. **LangChain 等构建层回答「怎么把一个 Agent 造出来」**——它提供 Chain / Agent / Tool / Memory 等组件，开发者拼装出可运行的应用。它的抽象是面向**构建者**的。

2. **ixxi 回答「怎么把一个 Agent 用起来、用出自己的资产」**——它不造 agent，也不拼装应用，而是为**已经存在的 agent（Claude / Codex / Hermes 等）**提供一个能力中间层：把「能力」定义为可迁移、可验证、可演化的对象，让同一个能力在不同 agent 上都能落地，个人积累的能力资产可随人迁移、跨 agent 复用。

3. **构建层给你「做出一个 agent」的能力，使用层给你「用好已有 agent」的能力**。两者不冲突、不替代：一个应用可以同时是「用 LangChain 构建的」和「跑在 ixxi 的使用层管理下」——ixxi 的 Capability 挂在 agent 之上，不干预 agent 内部的构建逻辑。

一句话差异化的核心：**构建层面向「造」，使用层面向「用」；能力是使用层的商品，应用是构建层的商品。**

## 二、对比矩阵

> 列 = ixxi + 5 个竞品；行 = 7 个维度。`—` 表示该维度上该工具无对应设计。

| 维度 | ixxi | LangChain | LlamaIndex | CrewAI | AutoGPT | Obsidian |
|------|------|-----------|------------|--------|---------|----------|
| **核心抽象** | Capability（能力对象）+ Adapter + Instance | Chain / Agent / Tool / Memory（构建组件） | Index / Retriever / Document（检索管道） | Crew / Agent / Task / Tool（多 Agent 编排） | 目标驱动自主循环（自动分解-执行） | 笔记 / 双向链接 / 插件（Markdown） |
| **面向谁** | 有多个 Agent、想积累跨 Agent 能力资产的个人使用者 | 构建 LLM 应用的开发者 | 构建 RAG / 检索问答应用的开发者 | 构建多 Agent 协作工作流的开发者 | 探索「给目标自动跑任务」的用户 | 个人知识管理 / 笔记用户 |
| **Agent 无关性** | **强**——能力层 Agent-neutral（I1），路由只引用 Capability ID（I5），三 Agent 平等，能力源唯一 | 弱——抽象绑定自身框架模型，Agent 是框架内的一等对象 | 弱——绑定检索/数据层抽象，可对接各模型但无独立能力抽象 | 中——可定义角色化 Agent，但跑在自己编排引擎上 | 弱——自带 Agent 运行时，任务形态固定 | 弱——无 Agent 能力抽象，人直接操作 |
| **能力可验证** | **有**——声明==实际（I3/I4）+ parity 六断言锁死 + 统一使用遥测 | 无内置——测试靠开发者自建 | 部分——检索质量可评估，能力验证无内置 | 无内置——靠端到端运行观察 | 无——自主执行难验证，结果质量依赖模型 | 无——笔记正确性无验证机制 |
| **边界演化** | **有**——开放注册（R-REG）+ 动态收敛（R-EVO）随使用演化，遥测驱动，人工裁决 | 无——边界由应用代码写死 | 无——边界由索引/管道结构决定 | 无——边界由编排定义决定 | 无——边界由任务目标决定 | 靠插件——功能边界由用户手动装插件扩展 |
| **内容隐私** | **强**——personal/ 不进 git + 敏感扫描 + 密钥走环境变量 | 中——数据由开发者自持，但偏应用层无内置护栏 | 中——数据自持，无内置隐私护栏 | 中——数据自持，无内置隐私护栏 | 中——数据自持，无内置隐私护栏 | **强**——本地 Markdown 文件，用户完全掌控 |
| **上手成本** | 中——需 init + 组织能力资产（能力抽象有学习曲线） | 中高——需学习框架组件模型 | 中——需理解索引/检索概念 | 中——需理解编排/角色概念 | 中——需给目标 + 配环境 | 低——装即用，Markdown 零门槛 |

**矩阵要点**（一句话读表）：

- **Agent 无关性 / 能力可验证 / 边界演化** 三行是 ixxi 的差异化所在——这几列只有 ixxi 是「有设计」而非「—」。
- **内容隐私** 一列 Obsidian 与 ixxi 同级，但 Obsidian 隐私来自「本地纯文件」，ixxi 隐私来自「分层 + 扫描 + 排除」的机制。
- **上手成本** ixxi 不占优——能力抽象是有门槛的，这是它偏向「长期积累」而非「即用」的诚实代价。

## 三、「ixxi 不是什么」清单

| # | 不是 | 说明 |
|:---:|------|------|
| 1 | **不是 LangChain 的替代品** | 不同层：LangChain 构建 agent，ixxi 使用 agent。使用层挂在 agent 之上，不替代构建层，也不被构建层替代 |
| 2 | **不是 RAG 框架** | 知识检索（kb-query）只是内置能力之一、参考实现，不是产品定位。ixxi 的核心是能力中间层，RAG 是其中一种可迁移能力，不是边界 |
| 3 | **不是多 Agent 编排器** | 不做 CrewAI/AutoGPT 式的「多 agent 协作分工」；「多 Agent 平等」指同一能力在 Claude/Codex/Hermes 上都是一等公民，与「编排多个 agent 干活」是两回事 |
| 4 | **不是知识库** | kb 系统是内置能力 + 参考实现，用来证明「能力可迁移/可验证/可演化」这套机制可用，不是要替代 Obsidian 等笔记软件 |
| 5 | **不是 AutoGPT 类自主 agent** | 不做 agent 本体，不做「给目标自动执行」的自主循环；决策保持三级制（用户 > 规范 > AI），「AI 帮你做，但不替你决定」 |
| 6 | **不是重型 harness 框架** | 不做 agent 运行时、不做 LLM 基础设施，只做「轻量 harness + 使用层」 |

> 一句话总括：ixxi 是「用好已有 agent」的中间层，不是「造 agent」「编排 agent」「自主执行」或「替代笔记工具」中的任何一类。

## 四、场景选择建议

### 选 ixxi 的场景

- 你**同时在使用多个 Agent**（如 Claude 为主、Codex/Hermes 换着用），希望同一套能力资产在两个 agent 上都能用、不用重写。
- 你想**长期积累自己的能力资产**（技能、规则、流程），并且要求它们可验证（声明即实际）、可演化（用得多留下、不用自动收敛）、可随人迁移。
- 你在乎**机制开源 + 内容私有**——通用机制公开，个人数据（反馈、画像、记忆）绝不出门。
- 你希望**人类保留决策权**——AI 帮你做，但不替你决定。

### 选竞品的场景

- **选 LangChain**：你是开发者，要从零构建一个自定义的 LLM/Agent 应用，需要丰富组件与生态（Chain、Tool、Memory、多模型对接）。
- **选 LlamaIndex**：你的核心需求是**文档检索问答（RAG）**——把一批文档索引起来、按需检索回答，需要成熟的检索管道。
- **选 CrewAI**：你需要**编排多个 Agent 协作**完成一项任务（角色分工、任务流），比如研究小组、写作流水线。
- **选 AutoGPT**：你想要一个**目标驱动的自主执行 Agent**，给定目标后由 AI 自动分解、执行、迭代，接受较高的不可控度。
- **选 Obsidian**：你只需要**本地笔记 + 双向链接 + 个人知识管理**，Markdown 零门槛，不需要任何 Agent 能力抽象。

### 边界说明（诚实对比）

- 若你**只需一个工具且不跨 agent**：Obsidian（笔记）或 LangChain（构建）或 CrewAI（编排）往往更直接——ixxi 的「能力中间层」设计对单工具、零迁移诉求用户是多余的抽象成本。
- ixxi 与竞品**可共存**：用 LangChain 构建的 agent 可以放进 ixxi 管理；用 Obsidian 记的笔记可以经 kb-ingest 提炼成能力资产。边界清晰，不抢生态位。
