> **给谁**：维护者（你）。

> 记忆锚点：**core/ 是「唯一真源」**。适配层（.claude/skills/kb-*、.agents/、.codex/）都是从 core 生成的副本，改只改 core，副本靠 sync 刷新。
>
> framework/ 下还有两个**适配层产物目录**（生成副本，不维护、不进 git）：`framework/.claude/`（Claude 平铺 kb-* + agents）、`framework/.agents/`（Codex 镜像 72 skill）。它们由 sync 从 core 生成，clone 后跑 sync 重新生成，`.gitignore` 排除。
>
> **边界澄清**：core/agents/ 是「ixxi 审查团」的权威源。各 Agent 引擎还自带**引擎原生 agent**（如 Claude 的 Explore/Plan/general-purpose），它们绑定引擎、不可迁移，不属于 ixxi 的能力，**不进 core/**。所以「Claude 环境里 agent 比 core/agents 多」是正常的——多出来的是引擎自带的。

## 二、改什么 → 跑什么

你改了东西之后，**喊我跑对应的验证**。这张表就是「改了什么该验证什么」的对照：

| 你改了什么 | 该验证什么 | 预期结果 |
|---|---|---|
| 改了 skill（core/skills） | 跑 sync 生成适配层 + parity | 73/73 全过 |
| 改了 agent（core/agents） | 跑 sync-agents + parity | 15/15 + 73/73 |
| 改了 hook（core/hooks） | 跑对应检查 + 确认路径引用没断 | — |
| 改了 AGENT.md | sync-agent-md.sh + 走 G 层修改流程 | — |
| 改了脚本（engine/scripts） | unittest | 59 tests OK |
| 改了配置（engine/config） | 跑依赖它的 check | — |
| 改了文档/目录结构 | 跑 check（断链/计数）+ 更新 README 目录树 | 零失败 |
| 改了任何能力源 | **一定跑 parity** | P1-P6 全过 |

> 一句话：**改了能力源（core/）就喊「跑 parity」；改了脚本就喊「跑测试」；改了文档就喊「跑 check」**。

## 三、疏忽检查清单（你的主战场）

这些是**你能对照发现的**，不用懂逻辑。每个都是「应该一致，不一致就是出了问题」：

### 1. 文档 ↔ 实际

- [ ] README 的目录结构 ↔ 实际 `ls` 结果（这次 README 就过时了）
- [ ] GETTING-STARTED 的步骤 ↔ 实际脚本（这次还写着 mkdir personal）
- [ ] 文档里引用的路径 ↔ 文件是否真的存在

### 2. 计数 ↔ 实际

- [ ] 文档里的 `count:xxx=N` 锚点 ↔ 实际文件数（改了文件数要同步）
- [ ] 「16 管理 skill + 57 外部」↔ 实际 core/skills 的目录数

### 3. 能力源 ↔ 适配层

- [ ] 改了 core/skills 后，适配层（kb-* 平铺、.agents、命令索引）是否重新 sync 了
- [ ] parity 是否还 73/73（这是「能力不缩水」的机器检查）

### 4. 个人数据 ↔ 零泄漏

- [ ] grep `29909` / `源质挽歌` / `D:/KnowledgeBase`，framework 要**零命中**
- [ ] grep 旧路径 `.claude/kb`，要零命中（neutral 化后不该再出现）

### 5. 措辞 ↔ 一致

- [ ] 禁用措辞（如「Hermes 无原生」「不运行领域 skill」）零残留
- [ ] 同一概念在不同文档里口径一致（如「三层分离」的层名）

### 6. 适配层产物 ↔ git 不跟踪

- [ ] `.claude/skills/kb-*`、`.agents/`、`.codex/`、`.claude/agents/` 不被 git 跟踪（`git ls-files` 应为 0）

## 维护时的通用提醒

1. **改 core/ 不手改适配层**——适配层是生成的，改了会被下次 sync 覆盖
2. **改完就跑对应验证**——别改完就提交，先验证（这正是不变量 G20「验证驱动完成」）
3. **发现不对劲就喊我**——不用自己修，你负责「发现」，我负责「修」
