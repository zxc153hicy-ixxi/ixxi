# ixxi 架构文档

> **给谁**：想基于 ixxi 做二次开发的开发者（包括未来的你）。
> **读完你能**：精确知道每个文件夹、每个重要文件是干什么的，以及「想加一个能力 / 改一个脚本 / 扩展一个 Agent」该动哪里、改完跑什么验证。
> **配套**：README（定位 + 三层架构高层）· 维护者手册（维护视角：改什么跑什么 + 抓错清单）。

---

## 一、分层总览

ixxi 是**单目录 + 内部分层 + git 隔离**。一个仓库里四层：

```
ixxi/
├── framework/    ① 开源通用层（机制，git 版本化，进 git）
├── personal/     ② 私有实例层（数据，.gitignore 排除，init 后生成）
├── framework/.claude/ .agents/ .codex/
│                 ③ 适配层产物（sync 从 core 生成，不进 git）
└── README.md / CHANGELOG.md / GETTING-STARTED.md / ixxi ...
                  ④ 门面文件（仓库级入口）
```

**核心不变量 I1**：能力源（core/）必须 Agent-neutral，不出现任何 `.claude` / Claude 专属语义。适配层（③）是 sync 脚本从 core 生成的副本，**改了会被下次 sync 覆盖，永远只改 core**。

**数据流**：`core/`（权威源）→ sync 脚本 → 适配层（.claude / .agents / .codex）→ 各 Agent 加载。`personal/` 是下游实例，永不回流 framework（除非走贡献回流流程，见 docs/guides/贡献回流流程.md）。

## 二、目录详解

### framework/core/ —— 能力源（最核心，Agent-neutral）

| 目录 | 内容 | 职责 |
|---|---|---|
| `skills/` | 15 管理 skill + `_external/` 57 外部 skill | **能力的权威定义**。每个 skill 目录含 `SKILL.md`（指令）+ `capability.json`（能力契约）。`_external/` 下按分类（创作-构思 / 创作-审查 / 创作-写作…）组织，跳过分类级重复 SKILL.md 后共 72 个 |
| `agents/` | 15 审查团 + `registry.json` + `supports.json` | 审查角色按 6 组组织：content（内容处理）/ design（设计审查）/ ops（运维审查）/ user（用户视角）/ curator（调度）/ _archived（归档）。`registry.json` 是 agent 注册表，`supports.json` 声明每个 Agent 支持哪些底层契约（不变量 I3） |
| `hooks/` | 4 组钩子 + `registry.json` | gate（提交前闸门）/ git（git 钩子：pre-commit、commit-msg）/ curator（技能化）/ auto（自动）。`registry.json` 登记所有 hook 的 trigger + script |
| `mcp/` | `README.md` + `schema.md` | MCP 预留位（schema 已建，接入待真实场景） |
| `onboarding.json` | 入门引导提示 | 首次触发展示，展示后标 fired:true |

### framework/engine/ —— 引擎（脚本 + 配置 + 测试）

| 目录 | 内容 | 职责 |
|---|---|---|
| `scripts/` | 48 个脚本（分类见下） | 所有机械操作：检查 / 同步 / 修复 / 迁移 / 扫描 |
| `config/` | `tag-taxonomy.yaml`（标签体系）、`cleanup-config.yaml`（版本清理）、`scene-registry-schema.md`（场景注册表 schema）、`evolution-config.yaml`（演化阈值） | 配置单一来源，脚本读配置不硬编码 |
| `templates/` | 导出 / 检查 / 会话模板脚本 | 可复用 shell 模板 |
| `tests/` | unit 52 + integration 5 + e2e 2 | 回归测试，改了脚本跑 tests |

**engine/scripts 分类**：

| 类 | 数量 | 代表 | 职责 |
|---|:--:|---|---|
| `check-*` | 21 | check-skill-parity / check-counts / check-links / check-health / check-hardcoded-paths | 检查（体检项、断链、计数、可达性） |
| `sync-*` | 6 | sync-skills-to-claude/codex/hermes、sync-agents-to-*、sync-agent-md | 从 core 生成适配层 |
| `fix-*` | 7 | fix-broken-links / fix-index-sync / fix-stale-paths | 修复（断链、索引、过时路径） |
| `batch-*` | 4 | batch-convert / batch-ocr / batch-mineru | 批量转换（文档/OCR/MinerU） |
| `migrate` / `schema` | 2 | migrate-tool / schema-migrate | 迁移（dry-run/rollback + schema 升级） |
| `gen-*` | 2 | gen-resources / gen-lifecycle | 生成 capability.json 的 resources / lifecycle_class |
| 其他 | 7 | scan-sensitive（安全扫描）、verify-capability（可执行性验证）、record-usage（遥测）、stats-unused（未使用统计）、auto-import（导入）、clean-inbox、cleanup-versions | 各专项 |

## 三、重要文件详解（二次开发必读）

| 文件 | 干什么 | 改它要注意 |
|---|---|---|
| `core/skills/<名>/SKILL.md` | 能力的权威定义（指令 + 流程） | 改完跑 sync + parity |
| `core/skills/<名>/capability.json` | 能力契约：requires（需要什么）/ provides（提供什么）/ tier / lifecycle_class / resources | 由 gen-resources/gen-lifecycle 生成，手改后跑 parity |
| `core/agents/supports.json` | 每个 Agent 声明的契约子集（I3） | 加新 Agent 时补声明 |
| `core/hooks/registry.json` | 所有 hook 的 trigger + script 注册 | 加 hook 要在这里登记 |
| `engine/scripts/check-skill-parity.py` | 能力源↔适配层可达性六项断言（P1-P6） | 能力不缩水的机器检查，挂 pre-commit |
| `engine/scripts/verify-capability.py` | 能力可执行性验证（tier + supports + dry-run，I2/I3/I4） | 比 parity 更进一步：验「能用」不只「可达」 |
| `engine/scripts/sync-skills-to-*.py` | 从 core 生成适配层（Claude/Codex/Hermes） | 改 SRC 路径要指向 core/ |
| `ops/rules/skill调度注册表.md` | 路由单一事实源：任务→能力→各 Agent 调用方式 | 三列（Claude/Codex/Hermes）都要填 |
| `AGENT.md` | 行为契约单一事实源（G/T/R 三层），CLAUDE.md/HERMES.md 由此生成 | G 层修改走四道拦截（警告+tag+CHANGELOG+校验） |
| `CHANGELOG.md` | 版本演进 | 每次发布更新 + 打对应 tag |
| `core/hooks/gate/version-check.sh` | 校验 CHANGELOG ↔ git tag 一致 | 发布时跑 |

## 四、二次开发路径（改哪里 + 改完跑什么）

| 想做什么 | 改哪里 | 改完跑什么验证 |
|---|---|---|
| 加一个能力（skill） | `core/skills/` 下建目录 + SKILL.md + capability.json | `sync-skills-to-claude.py` + `check-skill-parity.py`（72/N 全过）+ 更新 skill调度注册表 |
| 加一个审查 agent | `core/agents/` 下建 .md + 更新 registry.json | `sync-agents-to-claude.py` + parity |
| 加一个 hook | `core/hooks/<组>/` 下建脚本 + 更新 registry.json | 跑对应检查，确认路径引用没断 |
| 改一个检查脚本 | `engine/scripts/check-*.py` | `python -m py_compile` + unittest（59 tests） |
| 改 sync 脚本 | `engine/scripts/sync-*.py` | 跑 sync + parity，确认 SRC 指向 core/ |
| 扩展能力契约字段 | capability.json schema + gen-*.py | 重跑 gen + parity + verify-capability |
| 加一个规则 | `ops/rules/` 下建 .md | `check-rules-integrity.py` |
| 改 G 层规则 | `AGENT.md` | 走 G 层修改流程（git tag + CHANGELOG + sync-agent-md.sh） |

**一条总原则**：改了能力源（core/）就喊「跑 parity」；改了脚本就喊「跑 tests」；改了文档就喊「跑 check」（断链 + 计数）。详见维护者手册「改什么跑什么」。
