# /kb-query —— 知识库精准问答

## 用途

收到知识领域问题后，强制走完整检索→消化→回答→反馈流程。禁止搜到就答、跳读、排列式搬运。

## 执行流程

### 1. 解析问题 → 匹配领域

从用户问题中提取 2-5 个关键词，匹配 `framework/engine/config/tag-taxonomy.yaml`：
- 如果关键词命中某个 domain 的 subdomains → 锁定该领域
- 如果命中多个 domain → 列出候选让用户确认
- 如果无匹配 → 降级为全局搜索（标注降级原因）

**同义词扩展**：如果 tags 过滤后零命中，查 `framework/engine/config/tag-taxonomy.yaml` 中的 `_synonyms` 映射表，用同义词重新检索。

### 2. 标签过滤 → 精准检索

用确定的 subdomain 标签 grep 过滤文章，结合内容关键词二次过滤：

```
grep -rl "tags:.*<subdomain>" personal/knowledge/learning/<domain>/ --include="*.md" | xargs grep -li "<content_keyword>"
```

同时利用交叉引用链：从已有高度相关文章底部的 `## 相关文章` 顺藤摸瓜。

**三级降级**：
- L1：关键词精确命中 taxonomy subdomain → tags grep → 最精准
- L2：命中 domain 但未命中 subdomain → 全文搜索该 domain → 标注"降级L2"
- L3：未命中任何 domain → 全局全文搜索 → 标注"降级L3"

### 3. 渐进阅读

按相关度排序，**先读前 3 篇核心文章** → 给出回答 + 告知总命中量 → 询问"够了，还是再读？"

用户判断：够了结束 / 不够加 N 篇 / 方向偏了重新检索。

禁止自行判定需要读多少。

### 4. 消化整合

- **禁止**："A 文章说…B 文章说…"的排列式输出
- **要求**：读完后用自己的理解重建知识体系，结构化呈现
- 如果不同文章对同一问题有不同观点，标注差异

### 5. 硬闸门自检

**在输出回答正文前，逐项检查。此步骤不可跳过。**

| 检查项 | 检测方式 | 不通过时 |
|------|------|------|
| 搬运句式 | 扫描正文是否含"文章说""提到""写道""介绍""讲解"等排列式关键词 | 重写为消化整合式 |
| 检索摘要 | 正文末尾是否有 `检索:` 开头行 | 补上 |
| 未读标注 | 命中数 > 实读数时是否标注遗漏 | 补上 |

**自检不通过→重写后再输出。** 这是硬闸门，不是建议。

### 6. 输出格式

回答正文后，**必须**附带以下模板块（格式强制，不可省略任何一行）：

```
---
检索: <关键词> → <领域> → 降级: <L1/L2/L3> → tags: [<标签>] → 命中 N → 实读 M
这个回答：准确 / 部分准确 / 不准？  检索方向：对 / 偏了？
```

如果命中数 > 实读数，在反馈行前追加：
```
还有 K 篇未读：[列表]，是否继续？
```

### 6.1 检索记录（强制，不可跳过）

每次完成回答后，**立即**追加一条记录到 `personal/data/sessions/kb-query-log.jsonl`：

```json
{"date": "<YYYY-MM-DD>", "query": "<关键词>", "domain": "<领域>", "level": "L1/L2/L3", "hits": N, "read": M, "synonyms_used": false, "feedback": "pending"}
```

此步骤不可跳过。没有这条记录，反馈闭环无法运转。

## 反馈处理

收到 Step 6 的反馈后执行。

### 收到"准确 + 对"

无需操作。记录 `[feedback: positive]`。

### 收到"不准"或"部分准确"

分析根因，分三种情况：

**情况 A：tags 不准导致检索偏了**

1. 定位涉事文章（从本次检索命中列表中找）
2. 重新读文章内容，确定正确标签
3. 输出修正确认行：
   ```
   🔧 tags 修正: [文件名]  [旧tags] → [新tags]  确认？
   ```
4. 用户确认 → Edit 文章 `tags:` 行
5. 如果 taxonomy 缺 subdomain → 追加到 `tag-taxonomy.yaml`
6. 修正后：`grep -rl "tags:.*<新tag>"` 验证同域其他文章是否需要同样修正

**情况 B：检索方向偏了**

1. 重新解析问题关键词
2. 按新方向重新走 Step 1-6
3. 对比两次结果，确认新方向更准确

**情况 C：回答质量差（搬运式输出、遗漏）**

1. 回到 Step 2 重读遗漏文章
2. 重新消化整合
3. 重新输出 + Step 5 自检

### 收到"偏了"

按情况 B 处理。

### L2 规则沉淀

同一类型修正累计 ≥2 次时，主动问：

```
此类问题已出现 2 次（上次: <date>, 本次: <date>）。
建议沉淀为 [正模式/反模式/规则更新]：[名称]。
是否写入？
```

用户确认后：写入 personal/system/patterns/ 或 personal/system/anti-patterns/ → 更新索引。涉及 G 层 → 走 G 层修改流程。

## 边界条件

| 场景 | 处理 |
|------|------|
| 知识库无相关内容 | 明确告知"知识库无相关内容"，不凭空回答 |
| tags 过滤后零命中 | 尝试同义词、近义词扩展关键词重搜（降级 L2→L3） |
| 文章内容与 tags 不符 | 标注 tags 可能不准，主动提出修正 |
| 上下文不足 | 精简输出，建议缩小问题范围 |

## 检索质量追踪

记录位置：`personal/data/sessions/kb-query-log.jsonl`（Step 6.1 强制写入）。

用途：
- L1 命中率：衡量 taxonomy 标签覆盖质量
- 同义词使用频率：衡量 `_synonyms` 映射表是否需要扩展
- 反馈趋势：发现系统性问题（如某领域 tags 反复被指出不准）

### Session-Close 联动

`kb-session-close` 在会话结束时扫描 `kb-query-log.jsonl`，对 `feedback: pending` 记录提示用户评价。若 `feedback: negative` 记录 ≥2 条且根因相同（同一 subdomain 的 tags 被反复指错），触发 L2 沉积提案，走 G15 主动沉积流程。
