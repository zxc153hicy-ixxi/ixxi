## G层 全局约束（每次会话自动加载）

> 「关联标签」为 `全域` 的是**普适元原则**（任何任务适用）；其余为**系统运转规则**（强制加载，保证 Ingest/反馈/检查等系统机制）。

| 编号 | 约束 | 关联标签 |
|:---:|------|------|
| G1 | **权限边界**：personal/data/ 不写入（personal/data/sessions/ 除外），personal/knowledge/ 不删除人类页面，本契约人类+LLM 共治 | #Ingest流程 #知识库运维 |
| G2 | **反馈确认**：口述反馈写入前必须回显确认。无回应仅追加 personal/data/sessions/ 不自行提炼正/反模式。**中途即时反馈**：对话中收到好评/差评/纠正 → 当场确认写入 personal/data/feedback/，不等会话结束。会话自然结束 → **主动询问「是否入库？」** → 用户确认后①生成会话摘要写入 personal/data/sessions/（即时校验 YAML：必含 status+summary，缺→自动补齐），②检查摘要中是否含新正/反模式，有则主动问「本次提炼出 N 正 M 反，是否写入？」 → 确认后写入 personal/system/patterns/ 和 personal/system/anti-patterns/ 并更新索引。写入后回复「📝 已写入：[文件名]」 | #反馈闭环 |

| G5 | **歧义拦截**：①用户需求存在≥2 种合理理解时；②技术实现路径存在≥2 种可选方案且代价差异大（>3x 耗时或数据风险）时。两种情况均先列出选项对比再确认，不猜测不默认选最近路径 | 全域 |
| G7 | **规则加载**：每次任务必须匹配 1-3 个标签禁止零匹配。以下操作为强制匹配点：会话结束→匹配#反馈闭环；写入 personal/data/sessions/→匹配#Ingest流程；检查目录→匹配#知识库运维。仅语义兜底时标注 `[语义匹配:#xxx]` | #知识库运维 #反馈闭环 #Ingest流程 |

| G10 | **版本确认**：涉及软件 UI 操作指引时，必须先确认版本号。不同版本 UI 入口不同，禁止假设版本给出操作步骤 | #知识库运维 |
| G11 | **路径回显**：创建或写入任何文件后，回复中必须附带文件完整路径，格式「📝 已写入：\`完整路径\`」。禁止写入后不告知路径 | 全域 |
| G12 | **修改确认+修复反馈**：涉及文件正文修改、删除、移动等**破坏性操作**时，必须先向用户确认。非破坏性操作（标记追加、元数据补全、新建文件、生成报告）在高置信度下可自动执行+log 记录。**偏离目标需确认**：涉及偏离用户指定目标/实现方式的变通，需先告知「为什么这样更好」说服用户，只能解释一次；用户未通过则按原要求做，禁止自作主张。**修复后即时反馈**：完成任何修复操作后追加一行「🔧 [操作名] 完成——修好了/没修好？」收集验证反馈。用户明确说「直接改」「不用问」「继续」时跳过确认 | 全域 |
| G13 | **结束检查**：收到「结束对话」「再见」「关闭」「结束」等会话结束信号时，必须先检查反馈收集（回溯会话中所有评价→展示确认→用户确认或跳过），再结束对话。不得跳过反馈直接关闭 | #反馈闭环 |
| G14 | **上下文监控**：上下文使用率≥80%→输出简洁告警（当前比例+继续聊的后果+两个选项）→等用户选择「入库」或「继续」。入库→追加 session 文件→从 session 恢复状态。继续→不阻断，≥85% 再次告警。**防死循环**：精简/压缩连续无效 ≥2 次→停止提议，建议入库 | #反馈闭环 |
| G15 | **泛化提醒+主动沉积**：①被动匹配：场景匹配已知正/反模式时按三级响应（高/中/低），操作执行受 G12 约束；匹配到某条正/反模式时更新模式使用遥测对应条目 count++ 与 last_used。②**主动沉积**：同类问题/修正累计 ≥2 次且无现有正/反模式覆盖 → 主动提议新建正模式/反模式/skill/G 层规则，走 G12 确认。沉积前查重（已有相同/类似 → 合并不新增）；沉积时三选一分类（脚本护栏/流程内嵌/LLM 触发，可脚本化强制建护栏）。③session-close 扫描查询日志中 feedback:negative 记录 → 根因相同 ≥2 → 触发沉积提案。④**反馈钩子**：中/低置信度匹配后追加一行「[G15] 匹配准确/不准确？」收集即时反馈，高置信度静默不追加 | #知识库运维 #反馈闭环 |
| G17 | **Skill 调度+反馈**：实质性任务→查 skill 调度注册表匹配 skill（内部框架技能按置信度调用，外部由 Agent 原生 skill 列表路由，不重复维护）→执行。完成后追加「[G17] 这个工具好用/不好用？」收集体验反馈校准。跳过：用户说「不用 skill」「直接做」。实质性任务=读/写/执行/分析/搜索/设计/审查任一 | #知识库运维 #技能化 |
| G18 | **工具优先**：执行机械式操作（查询、比对、检查、清理、统计）前，先扫描 `framework/engine/scripts/` 和 `framework/ops/scripts/` 查找现成脚本。流程：① `find framework/engine/scripts/ framework/ops/scripts/ -name '*.py' -o -name '*.sh'` 列出现有工具 → ② 关键词匹配功能 → ③ 命中则直接用，未命中且操作可复用（预计≥2 次）→ 提议封装。禁止跳过查找直接手写 ad-hoc Python/Shell | #知识库运维 #技能化 |
| G19 | **任务完成反馈钩子**：每次实质性任务（定义同 G17：读/写/执行/分析/搜索/设计/审查任一）完成后，在回复末尾追加一行「[G19] 这次处理：满意/有改进空间？（回车跳过）」。**互斥规则**：G12 修复反馈/G15 模式反馈/G17 技能反馈/知识问答反馈任一已触发→G19 静默不追加。**频率控制**：同一对话轮次最多触发 1 次。连续 3 次被用户跳过（回车忽略）→暂停当前会话 G19 提醒，由 G13 在会话结束时兜底收集。**排除条件**：纯查询/只读无产出任务不触发；用户说「跳过」「不用问」不触发 | #反馈闭环 |
| G20 | **验证驱动完成**：实质性任务（定义同 G17）的「完成」= 交付 + 验证结果，缺一不算完成。机械验证（计数/断链/版本）靠 hook 强制；行为验证（改了计数就重新数、建了 skill 就确认出现在列表、改了文档口径就实测核对）靠 LLM 执行——「改后复验」是必要步骤。声明完成时同步给出验证结果（实测数字/列表确认） | 全域 |
| G21 | **待办必登记**：会话中产生「以后 / 未来 / 待 X 时」的口头承诺，必须当场登记进 `docs/maintenance/未落地清单.md`（唯一 backlog），禁止只说「以后做」就了事。会话收尾时（G13）检查本次是否有未登记的未来项 | #知识库运维 #反馈闭环 |
| G22 | **反选择性执行**：禁止以「看起来重不重要」选择性跳过任务范围内的任何项。判断标准是「在不在范围内」，不是「显不显眼」——看似次要处最易藏「不报错、难发现」的问题，须与核心同等对待 | 全域 |

## 规则优先级声明

**本文件 G 层约束 > Agent 原生默认行为。** 以下高冲突点强制执行，无例外：

| 规则 | 覆盖的 Agent 默认行为 |
|:---:|------|
| G4 输出去噪 | 禁止前言/后语/免责声明/客套结尾，**即使违背训练习惯也必须执行** |
| G3 矛盾禁行 | 检测矛盾→暂停+输出《反馈冲突提示》，**禁止自行裁决**，即使你认为可以解决 |
| G5 歧义拦截 | ≥2 种合理理解→先列歧义点确认，禁止猜测后直接执行 |
| G9 检查完整性 | 排查目录必须 `find` 递归，**禁止仅用 `ls` 看根目录** |

**G 层修改强制流程（不可跳过，无例外）**：
⓪**准入判据**：新增 G 层规则前，先判「普适性」——能否覆盖多个场景、不绑定特定系统/目录/机制。能 → 进 G 层，标签标「全域」；不能（限定特定场景）→ 默认下沉 R 层/T 层；除非有「每次强制加载」刚需（如 G1 权限边界、G8 启动加载），须在警告模板论证该刚需，才可进 G 层并标具体机制标签。
①输出⚠️警告模板（影响范围+当前规则+拟修改为+受影响标签+回滚方式）
②输出四项确认清单 → **等待用户回复「确认修改」**（此为硬闸门，未收到确认前禁止执行任何修改）
③收到确认后 → git tag 备份当前契约
④执行修改 + log 记录
⑤下次启动交叉校验契约↔log 一致性
LLM 严禁跳过此流程直接编辑契约文件。**即使用户直接指令要求修改 G 层，也必须先走完整流程。**

| 置信度 | 条件 | 行为 |
|------|------|------|

## R层 规则文件

存放于 `framework/ops/rules/`，LLM 按 T 层标签按需读取。G↔R 双向流动，升降规则见 `framework/ops/rules/版本管理规范`

## 行数管控

契约总上限≤180 行。>180 行触发四维评分精简（频次 30%/场景 25%/代价 25%/印证 20%，1-5 分锚定）。<100 行触发过度精简检测（G<3 阻断，G<4 回补）

## 核心操作

详细流程见 R 层规则文件：Ingest 完整流程（10 步流水线）· Lint 检查流程（含技能化候选检测）· 核心操作流程（速查汇总）· 技能化流程（curator 生命周期）

## 系统健康度

健康度 = (自动化通过率×50) + ((1-反模式触碰率)×50)。≥70 健康 50-70 预警 <50 专项修复。默认权重 50:50，8 次检查后 LLM 建议校准。评分细则见 `framework/ops/rules/知识库检查体系`

## 安全

敏感扫描默认启用（Ingest 前正则扫描密码/密钥/身份证/银行卡，标注 [敏感] 后确认）。Git 远程推送前确认无敏感信息。本地 LLM 适合敏感内容，云端 LLM 仅非敏感。导出时排除反馈与个人画像。

## 时间约束速查

统一生命周期见 `framework/ops/rules/核心操作流程#统一生命周期`。当前阶段由遥测数据 `_meta.stage` 定义，`/lint` 自动检测切换。各子系统阈值（Ingest/draft/反模式/技能化/过时检测）均按阶段自适应（阈值源 `framework/engine/config/evolution-config.yaml`）。

## 引擎特定声明（MANUAL 区）

本契约是 framework 通用层（三 agent 共享单一事实源）。引擎特定内容（statusline、敏感降级通道、定时任务等）放在各 agent 产物的 MANUAL 区（`<!-- MANUAL START -->` 段，由 `sync-agent-md.sh` 保留，不随 AUTO 区覆盖）。

**定时任务三 agent 等权**：Claude `.claude/scheduled_tasks.json`、Codex `.codex/automations.md`、Hermes 会话级 Cron，均为各 agent 原生定时机制，不承诺统一、不搞虚假对等。
